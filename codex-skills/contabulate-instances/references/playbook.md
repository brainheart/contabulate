## Workspace and donor map

Verified 2026-07-21 against `/Users/klaus/Projects/contabulate`.

The top-level `contabulate` repository is the landing-page hub. Its local `.git/info/exclude` ignores `/instances/`. Every directory under `instances/*-contabulate` has its own `.git`, branch, remote, history, and deployment. A clean hub status says nothing about instance changes.

Use repository-relative paths in implementation and reporting; do not bake this absolute path into product code.

Choose donors by behavior and corpus topology:

- `instances/austen-contabulate`: clean recent prose instance built from scratch; seven works, chapter/paragraph hierarchy, integrated metrics and metadata generation.
- `instances/tanakh-contabulate`: richest history of shared table advances; vocabulary views, drills, history sync, filters, metrics, commentary, Unicode normalization.
- `instances/kjv-contabulate` or `luther-contabulate`: Bible hierarchy plus readable commentary records.
- `instances/shakespeare-contabulate`: character rows and character-detail behavior.
- `instances/melville-contabulate` or `hawthorne-contabulate`: large multi-work prose corpora.
- `instances/homer-contabulate` or `aeneid-contabulate`: poetry with book/line hierarchy.
- `instances/xenophon-contabulate` or `thucydides-contabulate`: Greek work/segment models.
- `instances/dante-contabulate`: canto/terzina hierarchy and DDP commentary counts.

Before copying, compare recent commits in the chosen donor and `tanakh-contabulate`. Shared improvements have historically been ported in batches, and corpus-specific follow-ups may land afterward.

## Before editing

Run read-only orientation in both repos:

```sh
git -C <instance> rev-parse --show-toplevel
git -C <instance> status --short
git -C <instance> branch --show-current
git -C <instance> remote -v
git -C <instance> log -10 --oneline
git -C <hub> status --short
```

Read the instance README, build script(s), `instance-meta.json`, `docs/instance.json`, `docs/CNAME`, Playwright config, and both Python and browser tests. Inventory source-text licenses before copying or downloading anything.

For a new repository, confirm naming, canonical subdomain, source repository URL, emoji, language label, creation date, corpus scope, and source license. Do not create DNS, repositories, pushes, or deployments without the relevant authorization.

## Corpus and build contract

Define these choices before adapting UI code:

- Corpus membership and order. Use a catalog file when there are multiple source texts.
- Hierarchy and labels: work/book/play, chapter/canto/act, paragraph/verse/line/segment.
- Stable identifiers. Keep canonical IDs human-readable where possible and separate them from sortable location keys when needed.
- Tokenization and normalization. Reuse the same tokenizer for indexes, counts, metrics, row search, and highlighting. Test NFC, diacritics, punctuation, apostrophes, hyphens, right-to-left text, and corpus markers.
- Segment boundaries. Prevent headings, Gutenberg boilerplate, footnotes, commentary markers, or parashah markers from silently becoming corpus tokens.
- Optional dimensions: character, genre, commentator, vocabulary n-grams.

Expected published shell:

```text
README.md
LICENSE
instance-meta.json
docs/
  CNAME
  index.html
  instance.json
  css/main.css
  js/
  data/
  lines/
tests/
playwright.config.js
package.json
```

Build layouts differ. Some instances use one root build script; ported instances use `scripts/build_data.py` followed by metric augmentation. Preserve the instance's documented command or replace it with one obvious top-level command.

Generate, do not curate, the large files under `docs/data` and `docs/lines`. Build ratio metrics from additive primitives so aggregation remains valid: for example sentence count, character count, rarity sum, hapax count, word count, and a clearly defined MATTR value. Keep denominator semantics explicit in column tooltips and tests.

Tests should pin corpus facts that catch parser drift rather than every generated byte:

- expected works and representative titles;
- exact or bounded segment and word totals;
- first and last canonical IDs and text presence;
- unique IDs/abbreviations and valid foreign keys;
- representative vocabulary and posting shape;
- alignment between `chunks` and `lines`;
- required metric fields and plausible aggregates;
- optional data present only when supported.

## Instance metadata contract

`instance-meta.json` is the curated source. It should contain:

```json
{
  "id": "short-id",
  "emoji": "📚",
  "title": "Display title",
  "tagline": "Display title Tabular Explorer",
  "language": "Language",
  "created": "YYYY-MM-DD",
  "url": "https://short-id.contabulate.org/",
  "source": "https://github.com/brainheart/short-id-contabulate",
  "text_label": "works",
  "segment_label": "paragraphs",
  "sample_queries": []
}
```

The build merges curated fields with computed values into `docs/instance.json`:

```json
{
  "schema": 1,
  "id": "short-id",
  "created": "YYYY-MM-DD",
  "updated": "YYYY-MM-DD",
  "stats": {
    "texts": 0,
    "text_label": "works",
    "segments": 0,
    "segment_label": "paragraphs",
    "words": 0,
    "distinct_words": 0,
    "commentaries": 0,
    "comments": 0
  }
}
```

Also copy emoji, title, tagline, language, URL, source, and sample queries. Move `text_label` and `segment_label` inside `stats` in the generated payload. Publish zeroes for unsupported commentary fields; the hub expects numeric totals. Keep `created` immutable and let a successful build set `updated`. Compute stats from the same generated structures that power the UI.

Create each sample query in the running app after the data is final. Verify it loads without console errors, reproduces the intended question, uses the canonical host, and survives a copy/paste or reload. Prefer one memorable question over filler.

## Hub update

The hub has two deliberate updates for a new instance:

1. Append the canonical base URL, including trailing slash, to `docs/instances.json`.
2. Append a readable corpus/language/URL row to the instance table in `README.md`.

Do not hand-edit `docs/index.html` with corpus stats. It fetches `<base>/instance.json` with a timeout and renders unavailable instances without breaking the table. Before declaring the hub update done, validate JSON, inspect the hub diff, and—after the instance is live—confirm the endpoint is publicly fetchable and CORS/static hosting behavior is normal.

## Verification matrix

Run in this order:

1. Build from the documented clean inputs.
2. Run Python build-output tests.
3. Run `python3 <skill>/scripts/audit_instance.py <instance>` before registration and add `--hub-root <hub> --require-hub` after registration.
4. Run Playwright tests using the configured local HTTP server.
5. Smoke-test default load, representative exact and regex searches, every supported granularity, a drill and Back, filter chips, sort, paging, full-result CSV, color-scale toggle, a copied deep link, and mobile overflow.
6. Compare generated diffs for surprising total or ID changes. Explain expected large data diffs.
7. Check `git status` independently in the instance and hub.

Do not use `npm test` blindly: some older `package.json` files still contain the default failing placeholder. Use `npx playwright test` unless the package explicitly defines a real test script.

## Failure modes and time savers

- Wrong repo: always use `git -C` or `cd` into the nested instance before status, diff, commit, or push.
- Stale donor: compare the donor's latest shared-feature commit with Tanakh and corpus-specific follow-ups.
- Branding-only fork: search for the donor's title, hostname, CNAME, source URL, IDs, labels, tokenizer assumptions, tooltip nouns, filenames, test counts, and README copy.
- Hand-edited metadata: fix the generator and rebuild; otherwise the next build erases the correction.
- Missing zero stats: emit `commentaries: 0` and `comments: 0` when absent.
- `created` drift: creation date is release history, not build time.
- Loading overlay hang: `.is-hidden` must win against overlay display rules, and the overlay must dismiss when required data settles, including failures.
- Scope loss: location/genre filters should follow appropriate granularity switches; word/bigram/trigram views share vocabulary scope.
- Misleading aggregation: derive ratios from summed numerators and denominators, not averages of averages.
- Incorrect CSV: export the filtered result set across every page, using visible columns in visible order.
- Giant diffs without explanation: inspect counts and IDs before accepting regenerated JSON.
- Incomplete hub work: `docs/instances.json` powers the page, while `README.md` remains the repository catalog; update both.
